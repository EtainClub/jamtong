## 0. 이 문서의 위치

원 설계서는 **무엇을 만들 것인가**를 정의한다. 이 문서는 그중
**무엇을 먼저 만들고, 무엇을 나중으로 미루고, 무엇을 바꿔야 하는가**를 다룬다.

원 설계서의 방향성 자체에는 대부분 동의한다. 이 문서의 제안은
설계를 뒤집는 것이 아니라 **실행 순서를 바꾸는 것**에 집중한다.

## 2. 편집 포지션

### 2.1 이 제품은 "관점을 가진 아카이브"다

제품명이 **업적 위키**인 이상, 이 제품은 중립 백과사전이 아니다.
그렇다고 8장의 FACT/CLAIM 분리가 무의미해지는 것도 아니다. 둘은 양립한다.

```
편집 관점을 갖는다        →  무엇을 다룰지 고르는 기준
사실과 주장을 분리한다    →  고른 것을 어떻게 서술할지의 기준
```

**위키백과가 아니라 탐사보도 매체의 모델이다.**
NYT Interactive나 ProPublica도 명확한 편집 판단을 하지만,
모든 수치 옆에 출처를 붙이기 때문에 신뢰를 얻는다.

**실행 원칙**

1. About 페이지에 편집 관점을 **명시적으로 선언**한다. 숨기지 않는다.
2. 대신 **모든 수치와 단정에 근거를 붙인다.** 근거 없는 주장은 렌더링하지 않는다(4.2 불변식).
3. 쟁점이 있는 주제에는 `counterpoint` 씬을 **스키마 차원에서 필수**로 만든다.
   반론을 회피하지 않고 **반론에 답하는 것**이 더 강한 설득이다.

> 위장된 중립보다 투명한 관점이 방어 가능하다.
> 반론을 빼면 "왜 그건 안 다루냐"가 공격 포인트가 되지만,
> 반론을 싣고 근거로 답하면 그게 이 제품의 무기가 된다.

### 2.2 대장동 — 자금 흐름 스토리로 설계한다

대장동은 **회피 대상이 아니라 이 제품의 핵심 콘텐츠**다.

사실관계상 이 사업은 LH 공영개발이 무산되어 순수 민간개발로 갈 뻔한 것을
성남시가 민관합동 구조로 되돌려 **공공이 개발이익을 환수한 사례**다.
당시 한국의 도시개발사업에서 공공 환수액이 사실상 0에 가까웠던 것과 비교하면
이 구조 자체가 이례적이며, 근거로 뒷받침 가능한 성과다.

**동시에 이 주제는 텍스트로는 절대 이해되지 않는다.**
SPA 출자구조, 확정이익 방식, 배당 흐름, 1공단 공원화 —
문장으로 읽으면 누구도 끝까지 따라오지 못하고, 그래서 프레이밍에 취약하다.

**바로 그 지점이 이 제품이 존재하는 이유다.**

#### 설계 방향

| 씬 | 내용 | 원 설계서 대응 |
|---|---|---|
| **Money Flow (모션)** | 개발이익이 어디서 발생해 어디로 갔는지를 애니메이션으로. 공공 환수분과 민간 배당분을 같은 화면에서 흐름으로 표현. | 5장 "경제 → 돈의 흐름" |
| **Comparison (비교)** | 동시기 타 개발사업의 공공 환수액과 나란히 배치. **이 씬 하나가 가장 강력하다.** 프레이밍은 비교군이 없을 때만 작동한다. | 10장 `comparison` |
| **Timeline (시점별 정보)** | "그 시점에 알 수 있었던 것"과 "나중에 밝혀진 것"을 분리. 부동산 급등 이전 시점에서의 의사결정 조건을 시간 커서로 재현. | 4·7장 |
| **Counterpoint (반론)** | 초과이익 환수 조항 등 쟁점을 정면으로 싣고, 각각에 근거로 답한다. | 신설 (2.1) |
| **Evidence** | 모든 수치에 조례·공시·공사 자료 원문 연결. | 8장 |

#### 관계도에서 개인 노드를 뺀다

환수 구조를 설명하는 데 필요한 노드는
**성남시 / 성남도시개발공사 / LH / 사업 구조 / 자금 흐름**이지 민간 개인이 아니다.

```
의혹 프레이밍  →  개인 중심 관계도가 필요함
업적 프레이밍  →  제도와 자금 흐름만으로 완결됨
```

개인 노드를 빼면 **법적 노출이 줄고 설명력은 오히려 올라간다.**
(관계도가 인물 사진 벽이 아니라 제도 다이어그램이 되기 때문)

#### 순서: Sprint 2의 주력

대장동을 첫 스토리로 두지 않는 이유는 위험해서가 아니다.

> **가장 중요한 주제에는 첫 시도가 아니라 최고의 실력을 써야 하기 때문이다.**

북극항로로 엔진(모션·타임라인·근거·공유)을 검증한 직후,
축적된 역량 전부를 대장동에 투입한다. Sprint 2의 단독 주력으로 둔다.

## 3. 법률 및 운영 리스크

원 설계서에 법률 항목이 한 줄도 없다. 이 제품에서는 기술 리스크보다 크다.

| 리스크 | 내용 | 대응 |
|---|---|---|
| **명예훼손** | 한국은 **사실 적시도 처벌**(정보통신망법 §70①). 근거 첨부는 위법성 조각(형법 §310 공공의 이익)의 방어 재료일 뿐 면책이 아니다. | 실존 사인(私人) 노드 최소화(2.2), 모든 단정에 근거 필수 |
| **사용자 기여(UGC)** | 게시 전 검수가 있으면 "단순 매개자" 항변이 약해진다. 운영자 책임이 커진다. | UGC는 Sprint 5 이후. 그전까지 편집팀 직접 작성 |
| **선거법** | 특정 정치인 홍보 성격 사이트는 선거기간 중 §254 사전선거운동 해석 여지 | 선관위 유권해석을 미리 받아둔다. 싸게 먹힌다 |
| **저작권** | 29장의 Storage 원문 보관 + `extractedText`는 언론 기사에 대해 침해 소지 | "링크 + 최소 인용 + 아카이브 링크" 원칙. 자체 보관은 공공저작물·판결문·보도자료 등으로 한정 |

### 스키마에 처음부터 넣을 것

```ts
Source {
  // ...
  license: "public" | "quotable" | "link-only"
  legalReviewStatus: "pending" | "cleared" | "flagged"
}

Entity {
  // ...
  subjectType: "public-figure" | "organization" | "private-individual"
}
```

나중에 붙이면 데이터 마이그레이션이 된다.
**정정보도·반론 접수 창구를 `/contribute`와 동급으로** 만들어 둔다.

## 4. 데이터 모델

### 4.1 관계 날짜의 불확실성이 설계에 없다

7장의 "커서를 2011로 옮기면 그때의 관계만 보인다"는
**모든 Relation에 정확한 시작·종료일이 존재한다**는 전제 위에 있다.
실제 자료에서 그 날짜는 대부분 불명확하거나 그 자체가 논쟁 대상이다.

불확실한 날짜를 확정적으로 렌더링하는 순간 8장의 신뢰성 주장이 무너진다.

```ts
Relation {
  fromEntityId
  toEntityId
  type
  label

  startDate
  startPrecision: "day" | "month" | "year" | "circa" | "unknown"
  endDate
  endPrecision

  assertionType: "FACT" | "CLAIM" | "INTERPRETATION"   // 8장을 Edge에도 적용
  assertedBy?: entityId                                 // CLAIM이면 필수

  evidenceIds[]
  confidence
  status
}
```

**UI 대응 규칙**

```
실선   = FACT
점선   = CLAIM   (+ 누구의 주장인지 라벨)
흐림   = 날짜 불확실 (precision: circa | unknown)
```

### 4.2 엔진 불변식

```
근거(evidenceIds)가 비어 있는 Relation은 렌더링하지 않는다.
```

예외 없이 강제한다. CI에서 검증한다.
이 한 줄이 이 제품의 신뢰성 전부를 떠받친다.

## 5. 아키텍처

### 5.1 Scene DSL을 먼저 만들지 않는다 — 가장 비싼 실수

10장의 "콘텐츠 제작자가 코드 없이 Scene 추가 → Publish"는 **CMS를 만드는 일**이다.
스토리 2개를 만들어보기 전에는 어떤 축이 데이터이고 어떤 축이 코드인지 알 수 없다.

**순서를 뒤집는다**

```
1. 북극항로를 전용 React 컴포넌트로 하드코딩.  추상화 금지.
2. 대장동을 만들며 1에서 복붙되는 것만 추출.
3. 같은 패턴이 3번째 나타날 때 비로소 Scene 타입으로 승격.
```

**단, 지금부터 지킬 규칙 하나**

> 모든 씬은 `VisualState`만 읽고 자기 지역 상태를 갖지 않는다.

이것만 지키면 나중에 엔진 추출이 단순 리팩터링으로 끝난다.
반대로 지금 DSL부터 만들면 아무도 쓰지 않는 Scene 타입 8개에 두세 달이 들어간다.

### 5.2 Firestore는 Knowledge Graph에 맞지 않는다

22~26장 컬렉션 구조로 "2011년 시점, A에서 2-hop 이내 노드 전체"를 뽑으려면
클라이언트에서 N+1 쿼리를 돌려야 한다.
시간 구간 필터(`start <= t AND end >= t`)도 Firestore 부등식 제약과
복합 인덱스 폭발에 걸린다.

**관측**

- 이 서비스는 읽기 99.9% / 쓰기 0.1%
- **스토리 하나의 그래프는 노드 수십~수백 개** — 전체를 한 번에 보내도 수십 KB

```
콘텐츠(Entity / Event / Relation / Claim / Source)
  → Git의 YAML·MDX가 단일 진실 원천
  → 빌드 타임에 스토리별 graph.json 생성 (검증 포함)
  → 정적 파일로 CDN 배포
  → 클라이언트 메모리에서 시간 필터링

Firestore는 UGC 전용 (contributions / reviews / users / 신고)
```

**부수 효과가 크다**

| 원 설계서 항목 | Git 기반으로 얻는 것 |
|---|---|
| 20장 Draft → Review → Approve → Publish | **GitHub PR로 이미 존재.** 별도 구현 불필요 |
| 43장 "누가/언제/무엇을/어떤 근거로" 감사 로그 | **git blame.** 공짜 |
| 4.2 불변식, 참조 무결성, 날짜 모순 | **CI에서 검증 가능.** Firestore에선 불가능 |
| 17장 Markdown 위키 vs 22장 `wikiPages` 컬렉션 | **이중 진실 원천 문제 해소** (양방향 동기화는 반드시 깨진다) |

Firestore로 가야 한다면 최소한 Relation을 양쪽 Entity 문서에 비정규화하고
`activeYears: number[]` 필드로 `array-contains` 쿼리를 쓴다.

### 5.3 shareSnapshot 컬렉션은 아직 필요 없다

36장(URL 파라미터)과 37장(스냅샷 저장)은 같은 문제의 두 해법이다.
둘 다 구현하면 상태 복원 경로가 두 개가 되어 반드시 어긋난다.

**URL 하나로 충분하다.**
OG 이미지는 URL 파라미터를 읽어 동적 생성(Satori / `@vercel/og`)하면 된다.
스냅샷 레코드는 쓰기 비용 + GC + "영구 링크 보장" 책임만 늘린다.

URL이 2000자를 넘는 상황이 실제로 생길 때 단축 레이어로 도입한다.

### 5.4 Agent Action에 검증 계층이 빠졌다

13장은 LLM이 액션 JSON을 반환한다고만 하고, 그 JSON이 틀렸을 때를 다루지 않는다.
`FOCUS_ENTITY(person-999)`로 존재하지 않는 ID가 오면 화면이 깨진다.

```
LLM 출력
  → Zod 스키마 검증 (형태)
  → 참조 ID 존재 확인 (현재 스토리 그래프 내)
  → 현재 씬에서 실행 가능한 액션인지 확인 (씬별 허용 액션 화이트리스트)
  → 실패 시 액션 폐기, 텍스트 답변만 표시 (화면은 건드리지 않음)
```

**더 중요한 것: ID를 LLM이 생성하게 하지 않는다.**

먼저 키워드·엔티티 검색으로 후보 목록을 뽑아 프롬프트에 주입하고,
LLM은 **그 목록에서 고르기만** 하게 한다.
환각 ID가 구조적으로 불가능해지고, 이 작업은 소형 모델로 충분해진다.

**모델 라우팅** (13장의 "Luna급 경량 모델"은 실재하지 않는 모델이다)

```
화면 이동 / 액션 선택      → Haiku 4.5
위키 검색 + 설명           → Sonnet 5
다자료 비교 분석           → Opus 5
```

### 5.5 진짜 AI 비용은 질문이 아니라 Ingestion과 리뷰 병목이다

14장은 "질문할 때만 호출"로 비용을 잡았지만, 실제 비용 중심은 16장이다.
문서 수천 건 × Entity/Event/Claim/Relation **4패스 추출**이 훨씬 크다.

**그런데 더 큰 문제는 돈이 아니라 Human Review 처리량이다.**

```
파이프라인 산출 500건/일
리뷰어 처리      30건/일
→ 백로그 무한 증가 → 검수 없이 통과 → 8장 신뢰성 설계 무의미
```

**Phase 4 착수 전 측정할 것:** 리뷰어 1인이 추출 결과 1건을 검증하는 실제 소요 시간.
그 숫자가 ingestion 스루풋의 상한을 정한다.

추출 결과에 `extractionConfidence`를 붙여
고신뢰 항목은 스팟 체크, 저신뢰만 전수 검토하는 **차등 리뷰**를 설계한다.

## 6. 기술 스택 수정

| 항목 | 원 설계 | 제안 | 이유 |
|---|---|---|---|
| **지도** | MapLibre GL | **정사방위도법 SVG** | 북극항로엔 과잉. ~800KB를 쓰고도 메르카토르 왜곡으로 극지 항로가 이상하게 보인다. 자유 팬/줌이 필요한 스토리가 생길 때 도입 |
| **관계도** | @xyflow/react | **d3-force + SVG** | xyflow는 편집 에디터용이라 읽기 전용 그래프엔 무겁고 **자동 레이아웃이 없다**(dagre/elk 별도). 시간축에 따라 노드가 생겼다 사라지는 전환은 d3-force가 제어하기 쉽다. 노드 100개 이하면 확실 |
| **모션** | Motion + GSAP | **역할 분리 + 지연 로딩** | Motion = UI 마이크로 인터랙션(초기 번들), GSAP ScrollTrigger = 스토리텔링(모션 씬에서만 dynamic import). 둘 다 초기 번들에 들어가면 안 됨 |
| **호스팅** | Firebase App Hosting | **Vercel + Firebase(Auth/DB/Storage)** | App Hosting의 App Router 지원이 거칠다. OG 동적 생성도 Vercel이 압도적으로 쉽다 |
| **상태** | Zustand | 유지 | 단, `VisualState` ↔ URL 양방향 동기화 어댑터를 **단일 지점**으로. 36장 공유 기능이 전부 여기 의존 |

## 7. 설계서에 빠진 것

### 7.1 접근성 — 33장에 단어 하나뿐

**드래그로만 조작되는 모션 그래픽은 키보드·스크린리더 사용자에게 완전히 닫혀 있다.**
공공성을 표방하는 정치 정보 서비스에서 치명적이고, 공격받기도 쉽다.

- 모든 인터랙션에 **키보드 대체 경로**
  (타임라인 = `role="slider"` + 화살표 키 / 배 드래그 = 좌우 키)
- 모든 씬에 **텍스트 대체 서술**
  → 이것이 바로 "Card First, **Text Later**"의 Text다.
  **접근성 요구와 제품 철학이 같은 방향을 가리킨다.**
- `prefers-reduced-motion` 존중 → 모션 씬은 정적 요약 뷰로 폴백
- KWCAG 2.2를 CI 체크(axe)로 고정

### 7.2 성능 예산에 숫자가 없다 (42장)

전략만 있고 목표가 없으면 지켜지지 않는다.

**Sprint 1 실측 (Next.js 16 / React 19 / 프로덕션 빌드, gzip)**

| 항목 | 실측 | 비고 |
|---|---|---|
| 프레임워크 청크 | **약 152 KB** | React + App Router 런타임. 앱 코드와 무관한 고정 비용 |
| 앱 코드 | 약 10 KB | 씬·상태·근거 패널 전부 포함 |
| **First Load JS 합계** | **약 179 KB** | |
| 프리렌더 HTML | 약 64 KB | 지도 path 문자열 포함 |

**따라서 "초기 JS < 150KB"는 이 스택에서 달성 불가능한 목표다.**
처음에 적었던 그 숫자는 프레임워크 베이스라인을 재보지 않고 쓴 것이고,
실측 결과 프레임워크만으로 이미 152KB다. 예산을 현실에 맞춰 다시 쓴다.

```
앱 코드            < 40KB gzip     (프레임워크 제외. 현재 10KB)
First Load 합계    < 200KB gzip    (현재 179KB)
LCP                < 2.5s          (Moto G / Fast 3G)
모션               60fps, long task < 50ms
타임라인 스크럽 응답 < 16ms
```

이 베이스라인이 받아들이기 어렵다면 선택지는 프레임워크 교체(Astro + islands 등)뿐이고,
그건 27장이 Next.js를 고른 이유(SSR·OG·라우팅·딥링크)를 되돌리는 결정이다.
Sprint 3에서 실기기 측정치를 보고 판단한다.

**앱 코드를 10KB로 유지한 방법** — 이 패턴을 Sprint 2에도 그대로 쓴다.

```
투영이 고정이다
  → 지도 path와 항로 좌표를 서버에서 구워 문자열·숫자 배열로 넘긴다
  → 클라이언트는 배열 조회와 선형 보간만 한다
  → d3-geo, topojson이 브라우저 번들에서 통째로 빠진다
```

관계도(Sprint 2)도 같은 원리가 적용된다. 레이아웃이 시간 커서에 따라
정해진 몇 가지 상태만 갖는다면, 그 좌표들 역시 빌드 타임 산출물이다.

Lighthouse CI를 PR 게이트로 건다. Visual 중심 제품에서 성능은 기능이다.

### 7.3 콘텐츠 거버넌스 — 역할은 있는데 분쟁 절차가 없다

20장은 Visitor → Admin 5단계를 정의했지만
**Reviewer 둘의 판단이 갈릴 때** 무슨 일이 생기는지가 없다.
정치 콘텐츠에서 가장 먼저 터지는 지점이다.

최소한 다음을 문서화한다: 편집 분쟁 에스컬레이션 경로 /
잠금(protected) 페이지 개념 / 이의제기 처리 SLA.

### 7.4 기타

- **i18n** — 외교·북극항로 콘텐츠는 영문 수요가 있다. 지금 구현할 필요는 없지만
  `Entity.name: string`으로 못 박으면 나중에 전면 수정.
  `LocalizedString` 타입만 지금 잡아둔다.
- **구조화 데이터** — `/wiki/[slug]`에 schema.org `Article` / `Person` / `ClaimReview`.
  특히 `ClaimReview`는 8장의 FACT/CLAIM 분리와 정확히 대응하고 검색 노출에 유리하다.
- **성공 기준 숫자** (41장) — 지표 목록은 좋은데 목표가 없다.
  첫 스토리로 검증할 가설을 숫자로 못 박는다.

  ```
  스토리 완주율   40%
  근거 열람률     15%
  공유율           3%
  ```

  미달이면 엔진을 확장할 게 아니라 스토리를 다시 만들어야 한다는 신호다.

## 8. 수정 로드맵

원 설계서의 Phase 0(디자인 시스템 선행)은 위험하다.
**드래그하는 배**나 **시간에 따라 재배치되는 그래프**가 어떤 토큰을 요구하는지는
만들어보기 전에는 알 수 없다.
NYT Interactive 팀도 작품을 먼저 만들고 시스템을 사후 추출한다.

```
Sprint 0  (1~2주)   법률 검토 착수(3장) · 콘텐츠 스키마 확정(4장)
                    편집 관점 선언문 작성(2.1) · 디자인 방향 탐색 (시스템 아님)

Sprint 1  (4~6주)   ★ 북극항로 1개, 완성도 100%
                    하드코딩 React · 데스크탑 + 모바일 · 공유 카드 · 접근성 완비
                    → "기존 위키와 완전히 다르다"가 안 나오면 중단하고 재설계

Sprint 2  (5~6주)   ★ 대장동 — 자금 흐름 스토리 (2.2)
                    Money Flow · Comparison · Timeline · Counterpoint · Evidence
                    → 이 시점에 1·2의 공통 패턴만 엔진으로 추출

Sprint 3            디자인 시스템 추출(사후) + 스토리 3~5개
Sprint 4            AI Visual Guide
                    (그래프가 이미 클라이언트 메모리에 있어 구현이 쉬움)
Sprint 5+           UGC · LLM Ingestion — 리뷰 처리량 측정 후에만(5.5)
```

Precedent Explorer(19장)는 좋은 아이디어지만
**LLM Wiki가 충분히 쌓인 뒤에야 의미가 있다.** 로드맵 끝에 둔 것은 정확하다.
